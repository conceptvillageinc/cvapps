# CV見積アプリ v2 ロードマップ（案件〜請求〜管理表）

2026-09-15 にいただいた全体像（PDF 6ページ）を、既存のデータ構造と照らし合わせて
整理したもの。※1〜※12 の相談事項への提案も含む。

---

## 1. 全体像の要約

現在のアプリは「クライアント → 見積」の2階層。これを

```
クライアント
  └─ 案件（受注見込み・発注見込み・完了予定日・入金予定日・支払予定日）
       ├─ 見積（複数可）
       │    └─ 印刷仕様（複数可）→ 見積依頼メール
       ├─ 納品書（見積の明細から選んで作る）
       └─ 請求書（納品書を1つ以上まとめる）→ 送付 → 入金確認
```

に広げ、案件の数字を集計して **売上粗利管理表・入出金予定表・クライアントカルテ** を
自動生成する。

**要となるのは「案件」の導入。** 見積・納品・請求・入金・管理表のすべてが案件に
ぶら下がるため、ここを最初に作る。

## 2. 相談事項（※1〜※12）への提案

### ※1・※4 ネット印刷のスクショ取込と、マスタへの自動登録・URL

**提案: 「見積で使った価格」と「価格マスタ」を同じものにする。**

いまは価格マスタが独立した画面で、見積からは「マスタに登録済みのセル」を選ぶだけ。
これを、見積の明細追加パネルに「ネット印刷ページから取り込む」を足し、

1. URL入力 or スクショ選択 → AIが価格表を読み取る
2. **その場で価格マスタに登録**（URL・スクショの両方を保存）
3. 読み取った価格表から使うセルを選んで明細に入れる

とする。マスタのレコードには `source_url` と `screenshot_url` の列がすでにあるので、
スキーマ変更は最小で済む。

URLは持った方がよい。理由は2つ。
- 「URLから更新」で後日の価格改定を追える（機能はすでにある）
- クライアントカルテ（※12）の「一次情報」になる。問い合わせ時に見積番号と一緒に示せる

### ※2・※5 印刷仕様を入力するタイミングとUI

**提案: 「印刷仕様」を明細とは別の入力欄として持ち、依頼メールはそこから生成する。**

いまのメール生成は明細行から仕様を組み立てているが、順序が逆になっている。
印刷所に見積を依頼するのは**価格が分かる前**なので、明細（価格）より先に仕様が要る。

流れを次のようにする。

```
印刷仕様を入力 → 依頼メール生成・送信 → 見積書PDFが届く → 取込で明細化（A-1）
```

旧形式の見積が持っていた `print_type / size / paper_type / quantities / color_count /
desired_delivery_date` の列がそのまま「仕様」として使える。新形式の画面に
**「印刷仕様」タブ**を追加し、これらを入力する。

1つの見積で「チラシ」と「ラベル」のように複数の印刷物を扱うことがあるので、
仕様は**複数持てる**形にする（`print_specs` テーブル、見積1:N仕様）。
依頼メールは仕様ごとに生成できる。

これが入ると、旧形式の画面（仕様タブ・印刷費タブ）は役目を終えるので、
**旧形式UIを廃止して新形式に一本化**できる。

### ※3 過去見積からの検索範囲

**提案: 既定は同一クライアント内、「他のクライアントも含む」で広げられるようにする。**

追加印刷はほぼ同じクライアントの同じ商品なので、既定を絞った方がノイズが少ない。
一方で「同じ仕様のチラシを別のクライアントでも」という場合もあるので、切り替えは残す。

検索結果には **前回の原価・売価・入稿先（印刷所 or URL）・見積番号** を出し、
選ぶと明細に複製される。明細には「前回: CV-2607-001 から複製」の印を残す。

### ※6・※7 Webサイト制作・システム構築のスプレッドシートインポート

**※6 提案: 固定テンプレートのシートを用意し、それを取り込む。**

列は明細（`line_items`）と1対1にする:
`大カテゴリ / 名称 / 数量 / 単位 / 単価 / 原価 / 備考`

アプリから「テンプレートをダウンロード」でき、記入後に貼り付け（CSV）または
Googleスプレッドシートを指定して取り込む。Sheets連携は工程管理表の出力でも使うので、
仕組みを共用する。

**※7 は実物を見てから判断したい。** 項目が数十行になる場合、

- 見出し行でグループ分け（テキスト行はすでにある）
- グループごとの小計行
- PDFの改ページ

が必要になる見込み。**実際のWeb案件の見積スプレッドシートを1つ**見せていただければ、
現行フォーマットのままでよいか、長尺用の体裁を分けるかを判断できる。

### ※8 複数納品書を1枚の請求書にまとめる

**提案: 請求書は納品書を1つ以上持つ（1:N）。明細は納品書ごとに見出しを付けて並べる。**

```
【納品書 D-2609-001】9/10納品 チラシ印刷
  チラシ印刷費 ……… 1,000枚 …… ¥46,000
【納品書 D-2609-003】9/25納品 ラベル印刷
  パッケージラベル印刷費 … 3,000枚 …… ¥90,000
                                  小計 ¥136,000
                                  消費税 ¥13,600
                                  合計 ¥149,600
```

納品書単位の見出しがあると、先方が自分の受領記録と突き合わせやすい。

送付はアプリから（メール送信の仕組みはすでにある。PDFを添付して送る）。
郵送の場合はPDF出力。**電子印鑑は「郵送用」を選んだときだけ非表示**にする。

ステータス: `送付前`（既定）→ `送付済`→ `着金済`。入金予定日を過ぎても着金していない
ものは `未入金` として赤系で表示。

### ※9 MF会計との連携（CSV）

**提案: 請求書確定と入金確認の2つのタイミングで仕訳を作り、MFの取込形式でCSV出力する。**

| タイミング | 仕訳 |
|---|---|
| 請求書を送付済にした | 売掛金 / 売上高 |
| 着金を確認した | 普通預金 / 売掛金 |

**MF会計の仕訳インポートの列構成は、会計事務所に確認が必要**（勘定科目の名称や
税区分の表記が事務所の設定に依存するため）。サンプルCSVを1つもらえれば、
それに合わせて出力する。

### ※10 目標との差分表示

**提案: 月ごとに「目標・見込み・確定・実績」の4本を1つの表と1つのグラフにまとめる。**

| | 意味 | 元データ |
|---|---|---|
| 目標 | 売上目標・粗利目標・最低粗利目標 | システム設定で月ごとに登録 |
| 見込み | 受注見込み金額の合計 | 案件 |
| 確定 | 請求書を送付済にした金額 | 請求書 |
| 実績 | 着金済の金額 | 入金確認 |

差分は「目標まであと ¥X（達成率 Y%）」の形で、色は3段階。

- 達成 → 緑
- 80%以上 → 黄
- 80%未満 → 赤
- **粗利が最低粗利目標を下回った月は、達成率に関係なく赤で警告**

グラフは月別の棒（見込み・確定・実績を並べる）に、目標を横線で重ねる。
これ以上凝ると見なくなるので、まずはこの1表1グラフで運用してから足す。

目標は「期」でも見たいはずなので、**決算月**を設定に持ち、期の累計も出す。

### ※11 支払いスケジュールの決め方

**提案: 既定を「完了予定日の翌月末」にし、案件ごとに変更できるようにする。**

入金予定日の既定（完了予定日の翌月末）と同じ考え方で揃える。
印刷所の多くは月末締め翌月末払いなので、既定のままで大半は合う。

段階的に精度を上げる。

1. まず: 案件に `支払予定日` を持たせ、既定は完了予定日の翌月末。手で変更可
2. 次に: 印刷所情報に `支払サイト`（例: 月末締め翌月末 / 翌々月10日）を持たせ、
   案件で選んだ発注先から自動で決める
3. 将来: 仕入先からの請求書を登録したら、見込みを実額に置き換える

### ※12 クライアントカルテ

**提案: 4つのブロックで構成する。既存のスプレッドシートを見て項目を合わせる。**

| ブロック | 内容 | 元データ |
|---|---|---|
| 基本情報 | 社名・担当者・連絡先・住所・備考 | clients（すでにある） |
| 売上・粗利 | 月別・期別の推移（表＋グラフ）。一覧画面でも並べて見られる | 案件・請求書 |
| 案件・見積一覧 | 案件ごとの見積・納品・請求の状況 | 案件 |
| 印刷履歴 | 商品ごとに、入稿先（印刷所 or ネット印刷URL）・原価・一次情報（スクショ／URL） | 明細 ＋ 価格マスタ（※1の設計が効く） |

「原価と一次情報が見える」は※1でURLとスクショを明細から辿れるようにしておけば、
カルテ側は集めて並べるだけで済む。

**現行のスプレッドシートを見せていただければ、項目名や並びをそこに合わせる。**

### 電子印鑑

見積書・納品書・請求書のPDFに載せる。印影の画像を Supabase Storage に置き、
PDF生成時に重ねる。「郵送用」のときだけ外す（※8）。

## 3. 進め方（6ステップ）

依存関係の順に並べた。各ステップの終わりに動作確認をしてから次へ進む。

| ステップ | 内容 | なぜこの順か |
|---|---|---|
| **S1 案件** | 案件テーブル・作成画面・見積との紐づけ。既存16件の見積には案件を自動生成して紐づける | すべての土台。ここが無いと納品・請求・管理表が作れない |
| **S2 見積フロー** | 印刷仕様タブ（※2・5）、ネット印刷取込→マスタ自動登録（※1・4）、過去見積からの複製（※3）、旧形式UIの廃止 | 日常業務で毎回使う部分。案件の次に価値が大きい |
| **S3 納品書・請求書** | 納品書（明細を選んで作る）、請求書（納品書をまとめる、※8）、電子印鑑、PDF、メール送付、ステータス | 請求まで通って初めて「業務が一巡」する |
| **S4 入金・会計** | 銀行CSVとの照合で着金を自動確認、MF会計向けCSV（※9） | 請求書が無いと照合できないので S3 の後 |
| **S5 管理表・カルテ** | 売上粗利管理表（※10）、入出金予定表（※11）、クライアントカルテ（※12） | すべてのデータの集計なので最後 |
| **S6 スプレッドシート連携** | Web/システム案件のインポート（※6・7）、工程管理表のSheets出力とクライアント共有 | 独立性が高く、他と並行できる。必要になった時点で |

S6 は他と依存が薄いので、Web案件の見積が先に必要なら前倒しできる。

## 5. 決めておきたいこと

- **案件番号の採番**: 見積番号 `CV-YYMM-連番` と揃えて `P-YYMM-連番` のような形でよいか
- **納品書・請求書の番号**: 同様に `D-YYMM-連番` / `I-YYMM-連番` でよいか
- **見積の「受注確度」「フェーズ」**は見積ではなく**案件**の属性に移す方が自然。
  移してよいか（既存データは案件を自動生成するときに引き継ぐ）
- **消費税の扱い**: 現状は税率10%固定。軽減税率や非課税の明細が出ることはあるか
